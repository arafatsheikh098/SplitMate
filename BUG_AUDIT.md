# Bug / Issue Audit

A line-by-line pass through the codebase after the final Step 4
commit (`9a0a4a9`).  Tests: 158 unit/property + 1 e2e pass, ruff
lint clean.  No format gate in CI (see "Style" at the bottom).

The findings below are ordered by severity.

---

## CRITICAL — broken in shipping behaviour

### B1. Idempotency keys are silently dropped at the route layer (G5 unmet)

**What:** The service layer (`splitmate.services.expenses.create_expense`)
accepts an `idempotency_key` parameter and the table
`idempotency_key` exists, but the HTML form
(`splitmate/templates/expenses/new.html.j2`) has no
`idempotency_key` field and the route
(`splitmate/web/expenses.py:100`–`134`) never reads or passes one.

**Repro:**

```python
c.post(f"/groups/{g_id}/expenses/new", data={
    ..., "idempotency_key": "abc-123",
})  # 303, expense created
c.post(..., "idempotency_key": "abc-123", ...)  # 303, SECOND expense created
```

The same `idempotency_key` posted twice via the form produces
**two** expenses.  The `IdempotencyKey` table stays empty.

**Impact:** G5 is unmet; the unique constraint in the
`idempotency_key` table is dead; the F3 spec promise ("A
client-generated idempotency key makes double-taps and retries
create one expense") is not honoured from the UI.

**Fix:** add `<input type="hidden" name="idempotency_key">` to the
form (the value can be a per-page UUID generated by the GET
handler, stored in the form's session or rendered as a hidden
field) and pass it through `expenses_create` to
`create_expense(idempotency_key=...)`.  Then add a service-level
test (`test_idempotency_key_dedupes.py`) that posts the same key
twice and asserts the second call returns the first expense.

---

### B2. `web/expenses.py:131` does not pass the multi-payer data the service supports

**What:** F3 requires "one or more payers with amounts that sum to
the total."  The service has `_coerce_payers` accepting
`payer_amounts` as a dict, but the form
(`splitmate/templates/expenses/new.html.j2:30`–`37`) only
exposes a single `<select name="payer_id">` + single
`payer_amount`.  The route handler only forwards `payer_id` /
`payer_amount` keys (`web/expenses.py:127`–`129`).

**Impact:** Users cannot record a single expense that was paid by
multiple people.  This silently breaks the F3 contract.

**Fix:** add per-member payer checkboxes/amounts to the form,
forward them in the `data` dict, and update `_coerce_payers` to
also accept the flat pattern `payer_<id>=<amount>` so the form
can post without a wrapper dict.

## HIGH — wrong-but-not-crashing

### B3. `services/_core.create_group` return-type annotation is wrong

**File:** `splitmate/services/_core.py:91`
**What:** Declared as `-> tuple[Group, Member]`, actually returns
`tuple[Group, Member, token]` (line 136).  Every test and the
route handler already destructure three values, so this works at
runtime — but a `mypy` pass would flag every caller, and any
refactor that adds a 4th return value would be a silent signature
drift.

**Fix:** `-> tuple[Group, Member, str]`.

---

### B4. `services/expenses.soft_delete_expense` uses deprecated `datetime.utcnow()`

**File:** `splitmate/services/expenses.py:469`
**What:** `expense.deleted_at = datetime.utcnow()`.  `utcnow()` is
deprecated since Python 3.12 in favour of
`datetime.now(UTC)`.  The stored value is also naive, while every
other timestamp in the schema is `DateTime(timezone=True)`, so
`expense.deleted_at` can be ambiguous on the wall-clock.
**Same issue:** `splitmate/services/settlements.py:204` for
`soft_delete_settlement`.

**Fix:**

```python
from datetime import UTC, datetime
expense.deleted_at = datetime.now(UTC)
```

---

### B5. Admin error states are silently swallowed

**File:** `splitmate/web/groups.py:274`, `:289`, `:328`
**What:** Three admin POST routes catch `ServiceError` and
`pass`:

```python
@router.post("/groups/{group_id}/members/virtual")
def add_virtual(...):
    ...
    try:
        services.add_virtual_member(...)
    except ServiceError:
        pass  # "Errors are surfaced by validation in the form; we just redirect."
    return RedirectResponse(...)
```

The comment is misleading: the form does **not** show errors on
this path because the route never re-renders the dashboard.  An
admin who tries to (a) add a virtual member with a name already
taken, (b) archive a member with a non-zero balance, or
(c) demote the last admin gets a silent redirect with no
feedback.  SCOPE F1.e / F2.b / F10 say the rules apply; the UX
violates them.

**Fix:** flash the error in the session or query string and
render a banner on the dashboard.  Minimum: append
`?error=<message>` to the redirect and read it in
`group_dashboard`.

---

### B6. No service-level test exercises the idempotency key

**What:** B1 makes this worse, but even at the service layer
there is no test that calls `create_expense(idempotency_key=K)`
twice and asserts the second call returns the first expense.
`tests/test_expenses_api.py` does not mention `idempotency_key`.

**Fix:** add `tests/test_idempotency_key.py` covering:

* same key twice → same expense
* different keys → two expenses
* the same key used by a different member → two expenses
  (constraint is `(group_id, member_id, key)`)

## MEDIUM — defence in depth / hardening

### B7. `_register_milestone_routers` swallows all exceptions

**File:** `splitmate/main.py:160`–`208`
**What:** Each block uses `except Exception: pass` so a real bug
in a router (syntax error, ImportError on a missing dep, a typo)
silently disables the route.  A deploy of a broken milestone
appears to work and only fails when a user hits the missing
route.

**Fix:** narrow to `except ImportError:` and let other exceptions
propagate, OR log the exception to `LOG.exception(...)` so it
shows up in production logs.

---

### B8. `web/groups.invite_revoke` double-fetches the group

**File:** `splitmate/web/groups.py:250`–`252`
**What:**

```python
_, _ = group_member                          # discards both
group = services.get_group_or_404(session, group_id)  # refetches same group
services.revoke_invite(session, group=group)
```

`group_member[0]` is already the validated group; we throw it
away and re-query.  Not a bug, but dead code.

**Fix:** `group, _ = group_member`.

---

### B9. `deps.get_lang` hard-codes the language list

**File:** `splitmate/web/deps.py:14`–`20`
**What:** `if cookie in ("en", "bn")` instead of using
`supported_languages()` (live, used by `main._read_lang`).  If a
third language is ever added to `splitmate/i18n/__init__.py`,
`main` accepts it but every route falls back to the default
language.

**Fix:** `from ..i18n import supported_languages; if cookie in supported_languages():`.

---

### B10. `services/idempotency.reserve_key` race on concurrent dup

**File:** `splitmate/services/idempotency.py:46`–`52`
**What:** On `IntegrityError` the function calls
`session.rollback()` and returns `None`.  In the call site
(`services/expenses.py:418`), the calling function then proceeds
to `session.commit()` — but the rollback already discarded the
in-progress expense too, so the user gets a successful response
even though no expense was created.  The retry will then create
a fresh expense because the key was also rolled back.

**Impact:** Two concurrent POSTs with the same key (one wins on
insert, the other rolls back) — only the survivor's expense is
ever written, but the rolled-back one silently returns 303
instead of 409.  Hard to trigger in practice (would need
concurrent same-key requests within the same DB transaction's
flush window), but the failure mode is wrong.

**Fix:** In `create_expense`, check the return value of
`reserve_key`; if it returned `None`, re-read the original
expense via `lookup_expense` and return that, instead of letting
the function commit a transaction that no longer has the new
expense.

---

### B11. `IdempotencyKey` orphans on seed reset

**File:** `splitmate/seed.py:84`–`88`
**What:** The reset only deletes
`IdempotencyKey WHERE expense_id IN (expense_ids)`.  A key row
where `expense_id IS NULL` (reserved but never attached) is left
behind.  Not reachable via the current seed (which never sends a
key), but the cleanup is incomplete for any future caller that
uses idempotency keys and crashes mid-way.

**Fix:** also `delete(IdempotencyKey).where(IdempotencyKey.group_id == gid)`.

## LOW — cosmetic / style

### B12. `csv_export.py` formats amounts as floats

**File:** `splitmate/services/csv_export.py:92`, `:100`, `:140`
**What:** `f"{p.amount_minor / 100:.2f}"` — integer is divided by
`100.0` and formatted.  The output is correct (no precision loss
in the displayed range) but technically uses `float` on the
rendering path.  SCOPE.md says "no floats anywhere on the wire";
CSV is a wire format for spreadsheets.

**Fix:** render the minor integer with `format_amount_plain` to
stay all-int (the `paisa`-style `1250.50` is fine; the integer is
just split into major/minor by hand).

---

### B13. `_safe_filename` collision on groups with no alphanumeric name

**File:** `splitmate/web/share.py:77`
**What:** If `group.name` is all non-alphanumeric (e.g. `৳৳৳`),
the function returns the literal `"group"` for every such group,
so two `৳৳৳` groups in the same browser get the same filename on
download.  Edge case; default fallback is intentional.

**Fix:** append `group.id` to disambiguate.

---

### B14. `web/expenses.expense_delete` / `_restore` exposes the wrong status when forbidden

**File:** `splitmate/web/expenses.py:181`–`184`
**What:** If a non-admin non-creator tries to delete, the route
returns 403.  An *admin* who is not the creator is allowed by
the current code, which is the documented behaviour.  Looks
intentional, just worth noting for F7.a: "creator or admin can
edit or soft-delete an expense" — yes, admin is OK.

Not a bug; flagging as a place to add a test if F7.a is ever
challenged.

---

### B15. `web/expenses.expenses_create` swallows `SessionError` exceptions

**File:** `splitmate/web/expenses.py:130`–`168`
**What:** Only `ServiceError` is caught.  Anything else (DB
integrity error, programming error) bubbles to FastAPI's
default 500 handler.  That is the *right* behaviour, but the
custom 500 page (`main.py:121`) doesn't show the error message
so debugging in production requires server logs.

Not a bug.  Mention only.

## Style (out of scope for bugs)

`ruff check .` is clean.  `ruff format --check` reports 31 files
that would be reformatted — but the project sets
`line-length = 100` and `format` defaults to 88, so the diff is
purely cosmetic.  No CI step enforces `ruff format`, so this is
expected.  If you want formatting to be canonical, add
`format = "ruff format ."` to `.github/workflows/ci.yml` and
either set `[tool.ruff] format.line-length = 100` in
`pyproject.toml` or `ruff format --line-length 100 .`.

## Suggested fix order

1. **B1** — add `idempotency_key` to the form, wire it in
   `expenses_create`, add `tests/test_idempotency_key.py`.  This
   is the only finding that contradicts a G-acceptance criterion.
2. **B2** — multi-payer form fields + flat `_coerce_payers` parser.
3. **B3, B4** — mechanical fixes (annotation, `datetime.now(UTC)`).
4. **B5** — surface admin errors to the dashboard.
5. **B6** — service-level idempotency test (independent of B1's
   UI fix).
6. **B7–B11** — defence-in-depth cleanups.

The rest can stay as-is.
